# Information Leaks

Information leaks expose details that help an attacker choose an attack, or disclose sensitive data directly. A version banner may reveal a vulnerable component; a debug response may reveal database credentials. Removing unnecessary disclosures reduces reconnaissance opportunities, but does not replace patching, authorization, or protection of secrets.

### Disable Telltale Server Headers

Inspect responses from the public endpoint, including redirects and failures generated by proxies. Headers such as `Server: ExampleServer/1.2` or `X-Powered-By` can identify implementation details. Suppress unnecessary banners where the server supports it. Check the edge proxy and application separately: hiding a header in one layer does not ensure another layer will not add it.

Treat this as information minimization. A server can still be fingerprinted from its behavior, and an attacker can attempt an exploit without knowing its exact version. Inventing a false banner provides no dependable security guarantee.

### Use Clean URLs

Prefer *clean URLs* such as `/accounts/settings` over routes that expose template names or implementation extensions. Routing should describe the resource, rather than require a public `.php`, `.asp`, or `.jsp` filename. This also makes implementation changes easier. Changing a URL does not protect the underlying endpoint: authorization must still apply to every request, including old routes that remain available.

### Use Generic Cookie Parameters

Default session cookie names can identify a framework. A generic name reduces that clue, but the cookie's scope and security attributes matter more than its name. Keep the session identifier opaque; never put credentials or internal configuration into a cookie value. See [Session Hijacking](SESSION.HIJACKING.md) for session protection and [CSRF](CROSS.SITE.REQUEST.FORGERY.ATTACKS.md) for cross-site cookie behavior.

### Disable Client-Side Error Reporting

Here, client-side error reporting means displaying server exception details to the browser. A production response must not expose stack traces, SQL text, filesystem paths, connection strings, or secret values. Return a generic message and an opaque request identifier; retain useful diagnostic details in access-controlled server logs. Redact secrets there as well. This separates troubleshooting from disclosure. See [OWASP Error Handling](https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html).

For example, replace a response containing `SELECT ...`, an internal database hostname, and a driver exception with:

```json
{"error":"The request could not be completed","request_id":"req_7d93"}
```

The identifier lets support correlate the failure with restricted logs. It must not provide public access to those logs. Exercise failures in middleware and upstream services as well as ordinary application handlers.

### Minify or Obfuscate JavaScript Files

A *minifier* compresses code; an *obfuscator* makes names and structure harder to read. The source proposes both as ways to obscure library choices. They can increase inspection effort, but anything delivered to a browser remains available to its user. Neither protects embedded API secrets, fixes a vulnerable dependency, nor enforces access control. Review production source maps and bundles as public artifacts. Keep privileged operations and secrets on the server.

### Sanitize Client-Side Files

Review HTML, templates, JavaScript, comments, and generated artifacts before release. A comment containing an internal hostname may reveal infrastructure; a bundled credential is an immediate credential exposure. Remove unused debug code and prevent configuration files, repository metadata, backup archives, and private source maps from being published accidentally.

If a real secret was published, remove it and revoke or rotate it. Deleting the comment alone does not invalidate copies already downloaded or cached. Review use of the exposed credential and affected services.

### Stay on Top of Security Advisories

Maintain an inventory of deployed components and respond to their security advisories. Header suppression and minification buy no guaranteed delay against exploitation. The source's definition of a zero-day as a flaw publicized within 24 hours is inaccurate; do not use that time window to prioritize patches. Track vulnerability impact and exposure instead. [Third-Party Code](THIRD.PARTY.CODE.md) covers dependency risks.

### Detection and Release Checks

The following is a repository checklist derived from the source's leak categories:

- Inspect headers, cookies, HTML, JavaScript, and source maps through the production delivery path.
- Trigger controlled 400, 404, and 500 responses in a test environment; verify that debug information stays private.
- Scan release artifacts for secrets, private addresses, internal comments, and configuration files.
- Verify that logs and diagnostics require authorization and that tokens and passwords are redacted.
- Repeat these checks after framework, reverse-proxy, or deployment changes.

A useful regression check asserts that a known failing request produces a generic response while preserving a diagnostic event for authorized operators. Do not log the complete sensitive request merely to make this check easier.
